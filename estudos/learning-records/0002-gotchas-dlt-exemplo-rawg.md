# Gotchas de dlt descobertos construindo o exemplo RAWG

Construindo o source real (exemplos/rawg/) contra dlt 1.30.0, vários comportamentos só aparecem rodando — ou lendo a spec da API com atenção:

1. ~~`incremental.last_value` avança ao vivo~~ **SUPERSEDIDO (ver 3):** a solução canônica não é congelar o cursor manualmente — é `row_order="desc"` no incremental, que faz o dlt parar de paginar, filtrar e deduplicar sozinho. (Comparar contra `last_value` dentro do loop de fato quebra na primeira página, pois ele avança ao vivo; o correto seria usar `start_value`, que não muda durante a execução — mas com `row_order` nem isso é necessário.)
2. **Transformer com `data_from=funcao` instancia o resource pai com os argumentos padrão.** Se o source passa `api_key` explicitamente ao pai mas o transformer declara `data_from=games` (função nua), o dlt resolve o pai com os defaults (`dlt.secrets.value`) e falha com `ConfigFieldMissingException`. Correção: vincular com pipe no source — `g = games(api_key=...)` e retornar `g | game_details(api_key=...)`.
3. **`row_order` no incremental é o mecanismo nativo para APIs sem filtro "since".** Docs de cursor-based incremental (exemplo GitHub Events): com `row_order="desc"` e dados ordenados por cursor, o dlt encerra o generator ao primeiro item mais antigo que o cursor do run, inclui empates, filtra o já carregado e deduplica pelo `primary_key`. Validado empiricamente no smoke test: run 1 carrega tudo (2 páginas), run 2 pede só 1 página.
4. **O pipe do transformer não achata batches.** O transformer recebe exatamente o valor yieldado pelo resource pai: se o pai yielda a página inteira (lista de itens), o transformer recebe uma lista — e `game_item["id"]` explode com `TypeError`. Correção: o pai que alimenta transformer deve yieldar item a item (`for page in client.paginate(...): yield from page`). Batches yieldados direto para tabela são achatados normalmente; o problema é só no fluxo do pipe.
5. **A API real da RAWG ≠ o que se supõe dela — e a spec Swagger é subespecificada.** Conferindo a spec OpenAPI oficial (api.rawg.io/docs/?format=openapi): `/genres/{id}` (GenreSingle) retorna o gênero com `description` — **sem lista de jogos** (a lista `/genres` traz um `games` resumido → nested table `genres__games`). O endpoint rico em aninhados é `/games/{id}` (GameSingle). O transformer do exemplo é `game_details` via `/games/{id}` — e como a resposta é um **objeto único**, o `data_selector` precisa ser `"$"`. **Run real (set/2026) revelou campos que a spec não lista:** `genres`, `tags`, `stores`, `ratings`, `short_screenshots`, `parent_platforms`, `clip`, `user_game`, `community_rating`, `description_raw`, `reactions` (dict numerado) etc. — 24 tabelas no total. E um detalhe traiçoeiro: no endpoint de **lista** `/games`, o objeto `platforms[]` usa as chaves literais `requirements_en`/`requirements_ru` (underscore simples da própria API), enquanto no `/games/{id}` o `requirements` é plano (`minimum`/`recommended`). Shapes crus verificados em `reference/rawg-shapes-reais.json`.
6. **Deduplicação do incremental acontece antes do transformer.** Run 2 do smoke test: o item que empata com o cursor já foi carregado, então o incremental descarta antes do transformer — `game_details` nem roda (2 requests só: genres + página 1). Mais econômico ainda que o esperado.

Também confirmado empiricamente: o destination `filesystem` faz fallback de `merge` para `append` (padrão clássico de lake); `dlt[duckdb]` não traz pandas/pyarrow (necessários para `.df()` e Parquet); a tabela interna de versão de schema no destino é `_dlt_version` (singular); e o DuckDB **não aceita `dataset_name` igual ao nome do catálogo** (arquivo `*.duckdb`) — gera `Binder Error: Ambiguous reference` no load (o smoke_test nunca viu isso porque `dev_mode=True` timestampa o dataset, tornando-o diferente do catálogo).

**Evidence:** `smoke_test.py` validou: carga completa (2 páginas), corte incremental na 2ª execução (só 1 página requisitada + sem requests de detalhe), cursor persistido correto, nested tables geradas (`games__platforms`, `game_details__platforms`, `game_details__metacritic_platforms`, `game_details__alternative_names`), merge sem duplicação, Parquet por tabela no lake local.

**Implications:** os exemplos dos slides mostram o padrão nativo (`row_order`) em vez de lógica manual de cursor — e o padrão manual vira contraponto didático ("o que você NÃO precisa escrever"). O gotcha do pipe no source permanece válido e vale um slide. O exemplo do transformer nos slides usa `game_details` (`/games/{id}`, `data_selector="$"`), nunca `genres/{id}`.
