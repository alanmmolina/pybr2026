Aula 4: Pipeline e Destination — carga, estado, refresh e staging

Objetivo: Dominar o ciclo de vida do pipeline — dev_mode, refresh modes, estado persistente, staging, retries — e como trocar destinos sem tocar na extração.
Requer: Aula 3.
Fonte primária: Pipeline e Destination (docs oficiais).

Pipeline: o orquestrador

O pipeline executa as três fases — extract → normalize → load (detalhadas na Aula 2) — e persiste artefatos no diretório de trabalho ~/.dlt/pipelines/<nome>/:

import dlt

pipeline = dlt.pipeline(
    pipeline_name="rawg",              # identidade persistente
    destination="duckdb",            # pode ser sobrescrito no run()
    dataset_name="rawg_data",         # schema/database no destino
    dev_mode=True,                  # adiciona sufixo datetime ao dataset
    progress="log",               # monitor de progresso
)

Dev mode

Quando dev_mode=True, cada execução cria um dataset com sufixo de timestamp (rawg_data_20260722_143000). Ideal para experimentação: você nunca sobrescreve dados de produção enquanto testa. Combine com destination="duckdb" em dev e o destino real em prod — o resto do código não muda.

Identidade do pipeline: nome, dataset e diretório

Três defaults que valem conhecer:

  • pipeline_name: se omitido, o dlt usa o nome do módulo em execução.
  • dataset_name: se omitido, vira {pipeline_name}_dataset (em destinos que têm dataset; fica vazio em vector DBs e ClickHouse).
  • Working dir: ~/.dlt/pipelines/<nome>/ — dois pipelines com o mesmo nome enxergam a mesma pasta e compartilham estado.

Para separar ambientes (dev/staging/prod) mantendo o mesmo nome, use pipelines_dir:

import os
from dlt.common.pipeline import get_dlt_pipelines_dir

dev_dir = os.path.join(get_dlt_pipelines_dir(), "dev")
pipeline = dlt.pipeline(destination="duckdb", dataset_name="sequence",
                        pipelines_dir=dev_dir)

O método run()

# Aceita source, resource, generator, lista, qualquer iterável
info = pipeline.run(
    data,
    table_name="tabela",               # opcional: força nome da tabela
    write_disposition="replace",      # sobrescreve o hint do resource
    refresh="drop_data",              # força refresh (veja abaixo)
    loader_file_format="parquet",    # formato do arquivo de carga
    schema_contract="freeze",         # sobrescreve contratos de todos os resources
)
print(info)  # LoadInfo com métricas da execução

O LoadInfo retornado traz, entre outras coisas: os load IDs criados, o schema aplicado e o pipeline — útil para programar reações (ex.: disparar dbt após a carga, como na Aula 6).

Refresh modes: resetando estado e dados

Três níveis de refresh, do mais leve ao mais destrutivo:

ModeEfeitoSchema afetado?
drop_dataTrunca tabelas do resource, reseta estado incrementalNão — schema preservado
drop_resourcesDropa tabelas dos resources, reseta estadoSim — histórico apagado, só a versão atual fica
drop_sourcesDropa todas as tabelas do source, reseta schema e estadoSim — limpeza completa
# Exemplo: refresh de uma tabela específica
pipeline.run(
    rawg().with_resources("genres"),
    refresh="drop_data",
)
# Trunca a tabela `genres` e recarrega o catálogo de gêneros.
# Outras tabelas do source (games, game_details...) não são afetadas.
Nuance importante

O truncate/drop acontece quando a fase de load começa — um extract ou normalize que falhe não afeta os dados no destino. E o refresh pode ser configurado sem tocar no código: PIPELINES__RAWG__REFRESH=drop_data python rawg.py.

Nota dos docs: forçar write_disposition="replace" como forma de refresh (o jeito antigo) não é mais recomendado — o argumento refresh faz isso de forma limpa, sem mutar o schema persistido.

O que o refresh faz por dentro

O refresh é transacional: o dlt só toca no destino se extract e normalize concluírem com sucesso. Sequência completa do drop_sources, passo a passo:

  1. Coleta as tabelas a dropar (as do schema do source no destino).
  2. Remove o estado do pipeline associado ao source.
  3. Reseta o schema do source.
  4. Roda extract + normalize (cria estado e schema novos).
  5. Antes do load, dropa as tabelas coletadas (staging + dataset).
  6. Remove o schema do source da tabela _dlt_version.
  7. Roda o load normalmente (tabelas recriadas, schema e estado novos persistidos).
drop_resources vs drop_data

drop_resources faz o mesmo, limitado aos resources processados — mas não apaga chaves de estado no nível do source (dlt.current.source_state()). drop_data só trunca (TRUNCATE), preserva o schema e, no incremental, reseta o cursor para o initial_value.

dlt.attach(): reconectando a um pipeline

Um pipeline é durável. Você pode reconectar a ele pelo nome para ler dados ou inspecionar estado — mesmo em outro processo:

import dlt

# Reconecta a um pipeline que já rodou antes
pipeline = dlt.attach(
    pipeline_name="rawg",
    destination="duckdb",
    dataset_name="rawg_data",
)

dataset = pipeline.dataset()
df = dataset.games.df()

Sincronizando estado com o destino

No início do run(), o dlt sincroniza o estado local com o destino. Em orquestradores como Airflow — onde cada task nasce com filesystem limpo — o dlt restaura o estado a partir do destino. A identidade do estado remoto é: nome do pipeline + localização do destino + dataset. Se você mantém o working dir entre execuções, pode desligar com restore_from_destination=false no config.toml; e dlt pipeline sync pede o estado de volta manualmente. Detalhes completos na Aula 5 (state).

Dataset API

O dataset expõe as tabelas como objetos lazy que você converte para o formato necessário:

dataset.tables                     # ['_dlt_loads', 'games', 'games__platforms', 'game_details', ...]
dataset.games.df()                 # pandas DataFrame
dataset.games.arrow()              # PyArrow Table (zero-copy)
dataset.game_details.to_ibis()     # Ibis expression (lazy, compilável para SQL)
dataset.row_counts()               # contagem por tabela

Destinations: trocar é trivial

O mesmo código de extração funciona em qualquer destino. O dlt cuida de:

  • Credenciais: lidas de secrets.toml ou variáveis de ambiente
  • DDL: CREATE TABLE no dialeto correto (Snowflake vs Postgres vs DuckDB)
  • Tipos: mapeamento automático (Python datetime → TIMESTAMP no Postgres, TIMESTAMP_NTZ no Snowflake)
  • Staging: S3/GCS/Azure para warehouses que exigem stage antes do COPY
  • Retries: carga idempotente por load job — rerun seguro após falha de rede
# De DuckDB em dev para Snowflake em prod: muda uma string
pipeline = dlt.pipeline(
    pipeline_name="rawg",
    destination="snowflake",   # era "duckdb"
    dataset_name="rawg_data",
)

Capabilities: nem todo destino faz tudo igual

Cada destination declara o que suporta (upsert, staged load, schema migration, etc.) e o dlt adapta a estratégia de carga automaticamente. Quando um warehouse exige staging, o fluxo vira:

extract → normalize → (upload para S3/GCS) → COPY/MERGE no warehouse

Para formatos abertos (Iceberg, Delta) e data lakes, o dlt escreve arquivos Parquet diretamente — sem engine intermediária.

As quatro formas de declarar um destino

Todas criam a mesma classe de destino; a diferença é onde você põe a configuração:

# 1. shorthand — só built-ins
dlt.pipeline("p", destination="filesystem")

# 2. named destination — o tipo sai do toml/env (troca de ambiente sem mexer no código)
dlt.pipeline("p", destination="my_destination")  # [destination.my_destination] destination_type=...

# 3. factory type string
dlt.pipeline("p", destination="dlt.destinations.filesystem")

# 4. factory importada — permite instanciar e nomear
from dlt.destinations import filesystem
azure = filesystem("az://dlt-azure-bucket", destination_name="production_az_bucket")
Named destination = troca dev→prod sem código

Em dev: [destination.my_destination] destination_type = "duckdb". Em prod, só o toml muda para "bigquery" + credenciais. O código fica intacto — o caso de uso clássico de ambiente.

Para inspecionar o que um destino consegue fazer: pipeline.destination.capabilities() (formatos de arquivo, tamanho máximo de identificador, recommended_file_size, naming_convention...).

Quando o dlt acessa o destino

O destino é acessado em apenas dois momentos:

  1. No início do run() — para sincronizar o estado do pipeline (ou pipeline.sync_destination() explícito).
  2. No load() — para migrar o schema e carregar o load package.

Consequência poderosa: extract e normalize não importam as dependências nem pedem as credenciais do destino. Você pode rodar cada fase em processos ou containers separados (multi-stage):

pipeline.extract(data, table_name="letters")     # nenhuma credencial de destino necessária
pipeline.normalize()                            # idem
pipeline.load(destination=filesystem(bucket_url=...))  # só aqui o destino é tocado

Naming convention por destino

O dlt traduz identificadores para o que cada destino aceita (padrão: snake_case). Mas cada destino tem regras próprias de case sensitivity:

DestinoCase sensitivity
RedshiftSem suporte a case-sensitive; converte tudo para minúsculas
SnowflakeCase-sensitive; upper case tratado como case-insensitive (default)
DuckDBSem case-sensitive, mas preserva o casing no information schema
BigQueryTudo case-sensitive

Você pode trocar a convenção (ex.: sql_cs_v1 para Snowflake case-sensitive), mas isso só afeta schemas novos — o dlt se recusa a re-normalizar identificadores de tabelas já criadas (use refresh para dropar).

_dlt_loads: linhagem e chaining

Cada execução gera um load package com um load_id único, registrado na tabela _dlt_loads com status = 0 (carga completa). Daí saem três utilidades:

  • Filtro de carga parcial: uma linha cujo load_id não existe em _dlt_loads ainda não foi concluída — dá para excluir dados de pacotes que nunca terminaram (importante em destinos sem transações longas, como Redshift).
  • Chaining de transformações: use o status como marcador — a transformação 1 pega status=0 e marca 1, a próxima pega 1 e marca 2...
  • Lineage: pipeline_name + load_id identificam a fonte e o momento de cada dado — a base do data vault.

SQL client: acesso de baixo nível

Além da Dataset API (mais amigável, vista acima), todo destino SQL expõe um cliente de baixo nível. O filesystem tem um especial que consulta seus arquivos via um DuckDB em memória:

with pipeline.sql_client() as client:
    with client.execute_query("SELECT id, name FROM customers WHERE id = %s", 10) as cursor:
        print(cursor.df())   # fetchall(), fetchone(), arrow(), iter_df()...

secrets.toml

O que é secreto fica em .dlt/secrets.toml; o que é apenas configuração fica em .dlt/config.toml. No exemplo do curso, só a chave da API é secreta — e o DuckDB nem precisa de credencial explícita (usa um arquivo local por padrão):

# .dlt/secrets.toml — só o que é secreto
# (seção [sources.rawg]: o nome do @dlt.source define o namespace)
[sources.rawg]
api_key = "COLE_SUA_API_KEY_AQUI"   # https://rawg.io/apidocs → Get API Key

# .dlt/config.toml — configuração que não é segredo
[destination.filesystem]
bucket_url = "file:///.../lake_local"   # para S3: "s3://seu-bucket/rawg" + env vars AWS

O dlt resolve a credencial/configuração correta automaticamente baseado no destination configurado. Nenhum if/else no código — e o secrets.toml nunca vai para o git (adicione ao .gitignore).

Custom destinations

Se os 20+ destinos não cobrirem seu caso, o dlt expõe a interface Destination para escrever o seu em Python — incluindo destinos não-SQL (vector DBs como Weaviate e Qdrant são implementados assim). É o tema central de extensibilidade da Aula 6.

Exemplo do curso: um source, dois destinos

No exemplo RAWG (exemplos/rawg/), o mesmo source carrega para DuckDB (dev) ou para um data lake Parquet (prod). Só muda o destination — e as credenciais saem de .dlt/secrets.toml / .dlt/config.toml:

# python rawg.py (dev): DuckDB no laptop
dlt.pipeline(pipeline_name="rawg", destination="duckdb", dataset_name="rawg_data", dev_mode=True)

# python rawg.py filesystem (prod): Parquet no lake
# .dlt/config.toml → [destination.filesystem] bucket_url = "file://.../lake_local"
# (para S3: troque por "s3://seu-bucket/rawg" + env vars AWS — nada mais muda)
dlt.pipeline(pipeline_name="rawg_lake", destination="filesystem", dataset_name="rawg_lake")
Nuance do lake que o destino filesystem revela

O destino filesystem não suporta merge — ele faz fallback para append (cada execução gera novos arquivos Parquet imutáveis). Isso é o padrão clássico de data lake: append-only + deduplicação no momento da consulta (DuckDB/Athena/warehouse). Warehouse faz merge; lake faz append.
