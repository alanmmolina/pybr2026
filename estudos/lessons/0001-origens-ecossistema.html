Objetivo: Entender quem criou o dlt, qual problema resolve, os princípios de produto, a trajetória de adoção e o estado atual do projeto e da comunidade.
Pré-requisitos: Nenhum.
Fonte primária: dlthub.com/docs/intro e o post Introducing dltHub (mai/2026).

O problema

Toda fonte de dados tem sua própria lógica de extração. API REST com paginação por cursor. Banco SQL legado sem chave incremental. Arquivo CSV que muda de schema a cada exportação. Cada uma dessas fontes gera um script diferente — e sem uma estrutura compartilhada, cada desenvolvedor resolve o mesmo problema de um jeito diferente.

O resultado é o que chamamos de "dialetos paralelos": scripts que repetem estratégias de formas incompatíveis dentro do mesmo time. Alguns times tentam resolver isso com templates e convenções internas. Mas convenções definem forma, não comportamento. Normalização de dados aninhados, carregamento incremental e gerenciamento de estado entre execuções exigem código que alguém precisa escrever, manter e evoluir. A convenção vira um framework caseiro — e o problema original retorna com outro nome.

Esse problema é medido, não só anedótico. Quando a dltHub pesquisou desenvolvedores em empresas Fortune 500, 95% acabavam escrevendo scripts Python customizados para ingestão de dados — não por escolha, mas porque as alternativas não serviam.

O diagnóstico da dltHub

Não existia um "equivalente a Jupyter Notebook, Pandas e NumPy para data loading" — uma ferramenta que casasse com o workflow e o skillset de quem já trabalha em Python. A dltHub decidiu construir uma. (fonte)

O que é dlt

dlt (data load tool) é uma biblioteca Python open-source que carrega dados de fontes diversas — muitas vezes bagunçadas — em datasets bem estruturados. É uma biblioteca, não uma plataforma. Você faz pip install dlt e a incorpora direto na sua codebase.

O dlt oferece comportamento e consistência de framework sem sacrificar a flexibilidade do Python. Com conceitos como resource, source, pipeline e destination implementados como decorators e funções Python puras, ele resolve os problemas repetitivos de ingestão e deixa você focar na lógica específica de cada fonte. A anatomia completa fica para a Aula 2.

Os quatro princípios de produto (do lançamento do 1.0)

No anúncio do dlt 1.0.0, o CTO Marcin Rudolf explicitou os princípios que guiam o projeto desde o início (fonte):

  • dlt é biblioteca, não plataforma. Você integra o dlt no seu código — não o contrário.
  • Multiplique, não adicione. Priorizar automação para eliminar tarefas repetitivas do usuário.
  • Sem caixas-pretas. Código aberto, limpo, intuitivo e hackeável.
  • Nós fazemos o trabalho para você fazer menos. O "princípio da empatia": minimizar o esforço de quem usa.

O corolário prático: o dlt respeita a plataforma que você já construiu, o conhecimento que seu time já tem, e promove autonomia e ownership. É por isso que ele se integra à Modern Data Stack em vez de substituí-la — detalhe na Aula 6.

O vetor agent-native

Em janeiro de 2025, a comunidade produzia ~2.400 pipelines por mês, 5% escritos por coding agents. Em janeiro de 2026: 81.000 pipelines/mês — crescimento de 34x — com 91% gerados por agentes (Claude, Codex, Cursor). Em setembro de 2025, foram 50.000 conectores customizados criados em um único mês, um aumento de 20x desde janeiro, impulsionado por desenvolvimento assistido por LLM.

O mesmo padrão aparece no consumo local: dispositivos únicos usando DuckDB via dlt cresceram 15x (de 3.923 para 58.306 por mês). O padrão "construir no laptop, rodar na cloud" virou o modo dominante de uso.

Por que o dlt é amigável a LLMs?

A arquitetura declarativa, modular e code-first do dlt — escolhida originalmente para humanos confiarem na biblioteca — é exatamente o que permite a um agente raciocinar sobre um pipeline de ponta a ponta. A documentação é estruturada para consumo por assistentes de IA, e o time corrige issues pensando no workflow de "copiar erro e colar no editor". (fonte)

dltHub: a plataforma (GA desde mai/2026)

Além da biblioteca open-source, a dltHub oferece uma plataforma gerenciada (dlthub.com) que pareia agentes que constroem pipelines dlt com o runtime que os coloca em produção:

  • AI Workbench: agentes Claude/Codex/Cursor geram, depuram e fazem deploy de pipelines.
  • Context layer: catálogo com 10.100+ fontes REST API pré-pesquisadas em dlthub.com/context, para o agente consumir como contexto.
  • Managed runtime: deploy com um comando (uvx dlthub-start), scheduling, alerting, observabilidade OTEL.
  • Transformations: agentes propõem transformações em Python que compilam para SQL (via Ibis) e rodam no DuckDB/Snowflake.
  • Building blocks: dlt + DuckDB + Marimo + Ibis — modular e composível, sem monólito.

Instalação

# Biblioteca open-source (suficiente para as próximas aulas)
pip install "dlt[duckdb]"

# Com extras para destinos específicos
pip install "dlt[bigquery]"     # Google BigQuery
pip install "dlt[snowflake]"    # Snowflake
pip install "dlt[postgres]"     # PostgreSQL
pip install "dlt[s3]"           # AWS S3 (staging)

# Ou com uv
uv add "dlt[duckdb]"

# Plataforma dltHub (separada da biblioteca)
uvx dlthub-start
Biblioteca vs plataforma — não confundir

dlt (a biblioteca): open-source, Apache 2.0, grátis, roda em qualquer lugar que rode Python. dltHub (a plataforma): produto comercial para deploy, observabilidade e workflows agentic. A palestra foca na biblioteca; a plataforma é opcional.
