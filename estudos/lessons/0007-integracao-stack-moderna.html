Aula 7: Integração na stack moderna — onde o dlt roda e com o que ele conversa

Objetivo: Mapear a superfície de integração do dlt: os orquestradores e plataformas de execução suportados, e as tecnologias (especialmente open source) com integração nativa — como source, destination ou auxiliar de pipeline.
Requer: Aula 6 (que já cobre a narrativa dlt+dbt/Ibis/DuckDB/marimo).
Fonte primária: Deploy a pipeline, Destinations, Verified sources e Running in production (docs oficiais).

O princípio: biblioteca, não runtime

O slogan oficial do deploy é direto: "dlt runs anywhere Python runs". O dlt não tem runtime próprio, agente, nem serviço que você precise hospedar — é pip install dlt dentro da sua codebase. Consequência direta: a orquestração é uma decisão sua, e o dlt se adapta a qualquer uma.

O que torna isso tecnicamente possível é o que vimos na Aula 5: o estado vive no destino. Cada invocação do pipeline é stateless — o orquestrador só precisa disparar pipeline.run() no horário certo, e o dlt retoma de onde parou (inclusive de outra máquina). É exatamente o que diz o callout do slide de orquestradores da palestra.

Dagster: a integração mais "nativa" de todas

Diferente dos demais (onde o dlt é só uma função Python agendada), o Dagster mantém um pacote próprio — dagster-dlt — com o decorator @dlt_assets que transforma um @dlt.source em assets materializáveis no Dagster:

# dagster-dlt: o source do dlt vira software-defined assets
from dagster import AssetExecutionContext, Definitions, load_assets_from_modules
from dagster_dlt import DagsterDltResource, dlt_assets

@dlt_assets(
    dlt_source=github_source(),
    dlt_pipeline=dlt.pipeline(pipeline_name="github_issues",
                              destination="duckdb", dataset_name="github"),
    name="github", group_name="github",
)
def github_assets(context: AssetExecutionContext, dlt: DagsterDltResource):
    yield from dlt.run(context=context)

defs = Definitions(assets=load_assets_from_modules([assets]), resources={"dlt": DagsterDltResource()})

Sources: o que o dlt já traz pronto

As fontes se dividem em duas categorias, e a diferença é de distribuição, não de qualidade:

Core sources — dentro da biblioteca

  • REST API — o RESTClient com paginação declarativa (o que usamos no exemplo RAWG, Aula 3).
  • SQL database — 30+ bancos via SQLAlchemy.
  • Object store & filesystem — S3, GCS, Azure Blob, arquivos locais.
  • Dataframe — pandas, PyArrow e Polars como fonte.

Verified sources — via dlt init

29 conectores mantidos pelo time e pela comunidade, distribuídos como código Python em repositório separado (dlt init <fonte> baixa para o seu projeto):

GitHub · Stripe · Shopify · Salesforce · HubSpot · Notion · Jira · Slack ·
Zendesk · MongoDB · Kafka · Postgres replication · Google Sheets/Ads/Analytics ·
Pipedrive · Facebook Ads · Airtable · Amazon Kinesis · Asana · Chess · Freshdesk ·
Inbox · Matomo · Mux · Personio · Scrapy · Strapi · Workable
Core vs verified

Core sources são genéricos e vêm integrados no dlt (por isso são os mais usados, segundo a telemetria oficial). Verified sources são específicos de uma API e ficam num repo separado — o dlt init traz o código para você customizar. E se nada servir, qualquer função que yielda dados é um source válido (Aula 6).

Dois destaques que importam para a stack moderna:

  • Formatos abertos + AI: o dlt escreve Parquet/Iceberg/Delta/Lance diretamente — e carrega para vector DBs (Qdrant, Weaviate) e Hugging Face Datasets, o que o coloca no caminho de dados para RAG e ML.
  • Trocar destino = mudar uma string (já visto na Aula 4): o mesmo source que alimenta DuckDB no laptop alimenta Snowflake em produção.
Nuance de licença (reforço da Aula 1)

A biblioteca é Apache-2.0, mas nem todo destino é open source: o Iceberg e o MS SQL Change Tracking são source-available (features da plataforma dltHub), e alguns destinos são serviços gerenciados (Snowflake, BigQuery...). Para a palestra, mantenha o foco no que é 100% open source.

Auxiliares: as peças open source que encaixam

Além de source e destination, o dlt integra nativamente com tecnologias que ajudam depois (transformação) e em volta (observabilidade) do pipeline:

  • Transformação — dbt: dlt faz EL, dbt faz T; o load_info dispara o job dbt após a carga (detalhado na Aula 6).
  • Transformação — Ibis + sqlglot: transformações Python que compilam para SQL e rodam no destino, zero-copy (Aula 6).
  • Intercâmbio in-memory — Arrow/Pandas/Polars: dataset.games.df(), .arrow(), .to_ibis() — o dlt respeita o padrão de composição do Arrow de ponta a ponta.
  • Notebooks/data apps — marimo: widgets nativos (schema_viewer, pipeline_selector) para exploração interativa (Aula 6 e o hands-on do exemplo).
  • Observabilidade: send_slack_message para alertas; Sentry (DSN em config.toml); traces OpenTelemetry via pipeline.last_trace; e os retry helpers que compõem com tenacity para retry com backoff exponencial.

O mapa mental para montar a stack

Tudo isso compõe um único padrão (o mesmo do diagrama final da Aula 6):

Orquestrador ──► dlt (EL) ──► destination ──► [dbt | Ibis] (T) ──► marimo/BI
(Airflow/Dagster/    │           (DuckDB/          │
 Prefect/... )       │            Snowflake/       │
                     │            Iceberg/...)     │
                     └──────────── estado vive aqui ┘

E uma última decisão de arquitetura, com a qual os docs são explícitos: o dlt suporta ETL e ELT, juntos. ETL = transformar antes de carregar (via add_map, @dlt.transformer — Aula 3); ELT = carregar cru e transformar no destino (dbt/Ibis). O padrão EL(T) da palestra é o mais comum: dlt extrai e carrega, e o "T" vira responsabilidade da ferramenta certa, com o compute do warehouse.
