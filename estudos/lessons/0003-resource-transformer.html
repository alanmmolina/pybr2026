Aula 3: Resource e Transformer — a extração em profundidade

Objetivo: Dominar o @dlt.resource — hints de schema, parametrização com secrets, dispatch para múltiplas tabelas, transformers, pipe operator e paralelismo.
Requer: Aula 2.
Fonte primária: Resource e Source (docs oficiais).

O Resource despido

Na essência, um resource é qualquer função que yielda dados. O decorator @dlt.resource transforma essa função em um objeto que o pipeline sabe extrair:

import dlt

@dlt.resource
def genres(client):
    # auth (?key=) e paginação (next) vivem no client, montado no source
    for page in client.paginate(path="genres", data_selector="results"):
        yield from page

# O resource é lazy: só executa quando o pipeline rodar
pipeline.run(data=genres(client=client))

Um resource pode yieldar dicts, listas, DataFrames, Arrow tables ou objetos Pydantic — o dlt normaliza tudo. Ele também é reutilizável: o mesmo resource pode rodar em pipelines diferentes, com parâmetros diferentes.

Standalone resources: sem decorator

Para dados que já estão em memória, não precisa de função: dlt.resource() aceita o iterável diretamente:

# Lista direta — sem função, sem decorator
# (campos do endpoint /genres conforme a spec Swagger da RAWG)
data = [
    {"id": 4, "name": "Action", "slug": "action", "games_count": 190000},
    {"id": 5, "name": "RPG", "slug": "role-playing-games-rpg", "games_count": 87000},
]
pipeline.run(data=dlt.resource(data, name="genres"))

Internals do resource: nomes dinâmicos, standalone e clones

dlt.resource como função e nomes dinâmicos

Você não precisa do decorator. dlt.resource também é uma função que embrulha um iterável — e o nome da tabela pode ser dinâmico, resolvido a partir dos argumentos da chamada:

# nome dinâmico: o resource assume o nome do stream
@dlt.resource(name=lambda args: args["stream_name"])
def kinesis(stream_name):
    ...
telemetry = kinesis("telemetry_stream")  # resource chamado "telemetry_stream"

Função decorada: chame o wrapper antes de usar

Quando o @dlt.resource decora uma função top-level de módulo, ele só embrulha a função — e você precisa chamá-la para obter o resource de verdade (a doc chama isso de "standalone resource"). É isso que permite parametrizar por chamada:

# fs_resource existe como função; chamar é obrigatório antes de extrair
pipeline.run(data=fs_resource("s3://my-bucket/reports"), table_name="reports")

compute_table_schema() e with_name()

Dois métodos que expõem o objeto DltResource que existe por baixo do decorator:

games().compute_table_schema()   # o schema que o resource geraria, sem rodar pipeline

O with_name() retorna uma deep copy renomeada do resource — ideal para reusar um resource genérico (ex.: leitor de CSV) em várias tabelas:

# mesmo leitor, duas pastas → duas tabelas independentes
reports_pipe = fs_resource("s3://.../reports") | csv_reader()
transactions_pipe = fs_resource("s3://.../transactions") | csv_reader()
pipeline.run([reports_pipe.with_name("reports"),
              transactions_pipe.with_name("transactions")])

O clone renomeado é totalmente separado do original ao carregar: mantém um resource state próprio e carrega para sua própria tabela.

Ajustando schema em runtime: dlt.mark

Há casos em que o schema só é conhecido quando os dados chegam — ex.: refletir uma tabela de banco dentro do DAG do Airflow. Para isso você emite hints junto com o primeiro item; o dlt os mescla no schema antes de aplicar contratos e persistir o load package:

@dlt.resource
def sql_table(credentials, schema, table):
    table_obj = reflect(credentials, schema, table)
    for idx, batch in enumerate(rows(table_obj)):
        if idx == 0:
            yield dlt.mark.with_hints(
                batch,
                dlt.mark.make_hints(columns=cols(table_obj), primary_key=pk(table_obj)),
            )
        else:
            yield batch

Dois utilitários relacionados no mesmo dlt.mark:

  • dlt.mark.materialize_table_schema() — cria a tabela sem linhas (útil para publicar schema antes dos dados chegarem).
  • dlt.mark.with_file_import(path, "csv") — importa CSV/Parquet/JSONL sem ler nem parsear; o dlt copia o arquivo como está para o destino.

add_limit com precisão: yields vs linhas

add_limit limita o número de yields, não de linhas. Se cada yield entrega uma lista de 15, limitar a 10 extrai 150 linhas:

my_resource().add_limit(max_items=10)                  # 10 yields (pode ser 10 páginas/listas)
my_resource().add_limit(max_items=10, count_rows=True)   # conta linhas e pula páginas vazias
my_resource().add_limit(max_time=10)            # para após 10s de extração
Limites que você não pode impor

Você não pode limitar um transformer — ele processa tudo que recebe para não deixar o dataset inconsistente. E add_limit substitui limites anteriores (não acumula); None/-1 desativa, 0 zera o resource.

Schema com Pydantic

Em vez de ditar coluna a coluna, você pode declarar o schema com um modelo Pydantic:

class User(BaseModel):
    id: int
    name: str
    tags: list[str]
    address: Address           # nested model → coluna json
    status: Union[int, str]   # vira bigint (primeiro tipo não-None)

@dlt.resource(name="user", columns=User)
def get_users(): ...

Regras: campo Optional → nullable; Union → primeiro tipo não-None; list/dict/model aninhado → coluna json (em vez de nested table). Para voltar ao comportamento padrão, use DltConfig = {"skip_nested_types": True}; e {"return_validated_models": True} entrega o modelo Pydantic (não um dict) ao transformer.

Métricas customizadas

@dlt.resource
def games():
    metrics = dlt.current.resource_metrics()
    metrics["page_count"] = 0
    for page in client.paginate(path="games"):
        metrics["page_count"] += 1
        yield from page

As métricas aparecem nos traces do pipeline (colunas custom_metrics__* na tabela resource_metrics). Alternativa funcional: resource.add_metrics(fn), que roda como passo de transformação sem alterar os itens.

Hints: declarando intenção

Os argumentos do decorator não são apenas configuração — são declarações de intenção que o dlt usa para gerar schema, controlar comportamento de escrita e validar dados:

@dlt.resource(
    name="game_details",                 # nome da tabela
    primary_key="id",                    # chave primária (merge/upsert)
    write_disposition="merge",           # append | replace | merge
    columns={
        "description": {"data_type": "text"},  # força tipo de coluna
        "ratings": {"data_type": "json"},     # força JSON em vez de nested table
    },
    schema_contract={"columns": "freeze"},    # rejeita colunas inesperadas
)
def game_details():
    ...
apply_hints: mudando hints em runtime

Resources que já existem podem receber novos hints com .apply_hints() — útil para sources de terceiros e para ajustes programáticos:

# Exemplo dos docs: forçar data_type json em coleções MongoDB
source_data = mongodb().with_resources("collection1", "collection2")
for col in ["collection1", "collection2"]:
    source_data.resources[col].apply_hints(columns={"payload": {"data_type": "json"}})

Parametrização e secrets

Sources e resources aceitam argumentos como qualquer função Python. Argumentos marcados com dlt.secrets.value ou dlt.config.value são injetados automaticamente do secrets.toml ou de variáveis de ambiente — zero if/else para ambiente no código:

@dlt.source
def rawg(api_key=dlt.secrets.value):
    # RAWG autentica pelo query param `key` — o client leva a chave
    client = RESTClient(base_url=API_URL,
        auth=APIKeyAuth(name="key", location="query", api_key=api_key))
    return genres(client=client), games(client=client)

# O dlt resolve api_key do secrets.toml ([sources.rawg]) automaticamente
pipeline.run(data=rawg())

Dica de palestra: isso é o que torna o mesmo código testável localmente (DuckDB + secrets de dev) e deployável em produção (env vars) sem mudar uma linha.

Dispatch para múltiplas tabelas

Um único resource pode enviar dados para várias tabelas com base no conteúdo. Dois mecanismos:

table_name como função

@dlt.resource(table_name=lambda event: event["type"])
def github_events():
    yield {"type": "PushEvent", "repo": "dlt"}
    yield {"type": "PullRequestEvent", "action": "opened"}

# Cada tipo vai para sua própria tabela: PushEvent, PullRequestEvent

dlt.mark.with_table_name

# Marca itens individuais com tabela explícita — útil com Pydantic
TABLE_MAP = {"click": "click_events", "purchase": "purchase_events"}

@dlt.resource(name="events")
def event_stream():
    for item in items:
        yield dlt.mark.with_table_name(item, TABLE_MAP[item["kind"]])

Transformer: recursos que se alimentam de recursos

Um transformer é um resource que recebe dados de outro resource. O caso clássico: uma API que lista IDs em um endpoint e detalhes em outro. A ligação se declara com data_from (instância padrão do pai) ou com o pipe | (instância configurada — o que o exemplo do curso usa):

# Resource "pai": lista jogos do endpoint /games
@dlt.resource
def games(client):
    for page in client.paginate(path="games", data_selector="results"):
        yield from page

# Transformer "filho": enriquece cada jogo com /games/{id}
@dlt.transformer
def game_details(game_item, client):
    return client.get(path=f"games/{game_item['id']}").json()

# O pipe liga o filho à instância configurada do pai; o dlt resolve a ordem
pipeline.run(data=games(client=client) | game_details(client=client))
Transformer é lazy e econômico

O transformer processa um item por vez (não espera o resource pai terminar). Em APIs com paginação, isso permite começar a enriquecer dados enquanto o pai ainda está extraindo — e evita carregar tudo em memória.

Transformer: return, async e a instância padrão

Um transformer pode retornar (não só yieldar) e pode ser async — inclusive um async generator, o que paraleliza os HTTP calls dos detalhes:

@dlt.transformer
async def pokemon(id):
    async with httpx.AsyncClient() as client:
        r = await client.get(f"https://pokeapi.co/api/v2/pokemon/{id}")
        return r.json()   # return, não yield

print(list([1, 2] | pokemon()))
data_from=funcao usa a "instância padrão"

Quando o transformer declara data_from=games (a função nua), o dlt conecta à instância padrão do pai — criada só com os argumentos default. Se o pai precisa de um client injetado (ou de qualquer argumento explícito), isso falha. É exatamente por isso que o exemplo do curso vincula com pipe no source (veja o callout lá embaixo): (games_resource := games(client=client)) (walrus no próprio return) e games_resource | game_details(client=client) — em keyword, porque o pipe entrega o game_item no primeiro argumento.

Pipe operator (|)

O pipe operator conecta recursos dinamicamente em runtime:

# Carrega só 100 jogos, com seus detalhes
pipeline.run(data=games(client=client).add_limit(max_items=100) | game_details(client=client))

# Funciona com listas também — o dlt cria um resource implícito
print(list([{"id": 3498}, {"id": 3328}] | game_details(client=client)))  # GTA V e The Witcher 3

Transformações inline: filter, map, yield_map

Recursos aceitam transformações encadeáveis sem sair do Python:

for game in (
    games()
    .add_filter(lambda game: game["rating"] > 4.0)                    # filtra
    .add_map(lambda game: {**game, "slug": game["slug"].upper()})   # transforma 1:1
    .add_yield_map(lambda game: game["platforms"])              # expande (1:N)
):
    print(game)
MétodoRelaçãoUso típico
add_filterN → N-Remover registros inativos, obfuscar antes de extrair
add_map1 → 1Renomear campos, anonimizar, converter tipos
add_yield_map1 → NExplodir arrays, gerar registros derivados

As transformações rodam na fase de extract — antes do schema ser computado. Use isso para pseudonimizar dados pessoais ou descartar colunas antes de qualquer coisa tocar o disco.

Paralelismo

Resources com parallelized=True são extraídos em threads paralelas. Async generators são automaticamente concorrentes:

@dlt.resource(parallelized=True)
def genres(): ...

@dlt.resource(parallelized=True)
def platforms(): ...

# Extrai genres e platforms em paralelo (endpoints /genres e /platforms)
pipeline.run([genres(), platforms()])

Nested hints: controlando tabelas aninhadas

Quando um resource tem dados aninhados, nested_hints permite definir chaves e referências nas tabelas filhas — transformando uma nested table em uma tabela de primeira classe com FK:

@dlt.resource(
    primary_key="id",
    write_disposition="merge",
    nested_hints={
        "purchases": dlt.mark.make_nested_hints(
            columns=[{"name": "customer_id", "data_type": "bigint"}],
            primary_key=["customer_id", "id"],
            write_disposition="merge",
            references=[{"referenced_table": "customers",
                         "columns": ["customer_id"],
                         "referenced_columns": ["id"]}],
        )
    },
)
def customers(): ...

Detalhes de como isso interage com merge e colunas _dlt_* na Aula 5.

Exemplo do curso: os resources da RAWG

O exemplo em exemplos/rawg/ usa tudo desta aula. O source monta o client (auth + paginação) e o injeta; o resource games combina incremental + merge; o transformer game_details enriquece cada jogo com o endpoint /games/{id} (objeto único, rico em aninhados: description, website, alternative_names, metacritic_platforms):

# source: autenticação e paginação no client, injetado nos resources
@dlt.source(name="rawg")
def rawg(api_key=dlt.secrets.value):
    client = RESTClient(
        base_url=API_URL,
        auth=APIKeyAuth(name="key", location="query", api_key=api_key),
        paginator=JSONLinkPaginator(next_url_path="next"),
    )
    return [genres(client=client),
        (games_resource := games(client=client)),
        games_resource | game_details(client=client)]

# resource: o cursor é dele — inline, como default do parâmetro
@dlt.resource(write_disposition="merge", primary_key="id")
def games(client, updated_at=dlt.sources.incremental(
        cursor_path="updated", initial_value="1970-01-01T00:00:00", row_order="desc")):
    for page in client.paginate(path="games", params={
        "ordering": "-updated", "page_size": 40,
    }, data_selector="results"):
        yield from page  # item a item — o pipe não achata batches

# transformer: o pipe entrega cada jogo em game_item
@dlt.transformer(write_disposition="merge", primary_key="id")
def game_details(game_item, client):
    return client.get(path=f"games/{game_item['id']}").json()  # objeto único
Detalhes que só aparecem rodando (ou lendo a spec)

1. O pipe não achata batches: o transformer recebe exatamente o valor yieldado pelo pai — se o pai yielda a página inteira (lista), o transformer recebe uma lista, não um item. Por isso games yielda item a item (for page ...: yield from page). 2. O pipe importa no source: sem ele, o dlt instancia o pai com os argumentos padrão — que aqui não existem (o client é injetado). 3. Endpoint certo para o transformer: o /genres/{id} retorna só o gênero com description (a lista /genres até traz um games resumido — vira a nested table genres__games); o endpoint rico em aninhados é o /games/{id} (developers, publishers, ratings, stores...). 4. Objeto único ≠ lista: /games/{id} devolve um objeto (GameSingle), não uma lista paginada — por isso client.get().json(), não paginate. O smoke_test.py valida tudo sem chave de API.
