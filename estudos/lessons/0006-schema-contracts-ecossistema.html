Schema contracts: controle do que entra

Por padrão, o dlt opera em modo evolve: novas colunas, tabelas e tipos são aceitos e o schema se expande. Ótimo para exploração — mas em produção você quer saber quando a fonte mudou. Os schema contracts definem o que fazer com dados inesperados, em três dimensões (tables, columns, data_type), cada uma com quatro modos:

ModoEfeitoQuando usar
evolveAceita e adapta: novas colunas, tabelas e tipos são bem-vindosDesenvolvimento, exploração de APIs novas
freezeLança exceção se dados não batem com o schema — nada é carregadoProdução, pipelines críticos
discard_rowDescarta a linha inteira que viola o schemaStreams com lixo ocasional; manter tabela limpa
discard_valueCarrega a linha, mas descarta só o valor que não se encaixaCampos novos irrelevantes; prioridade é não perder a linha
@dlt.resource(
    schema_contract={
        "tables": "evolve",        # permite novas tabelas
        "columns": "freeze",       # rejeita colunas inesperadas
        "data_type": "discard_row", # descarta linhas com tipo divergente
    }
)
def games(): ...

# Shorthand: "freeze" vira {"tables": "freeze", "columns": "freeze", "data_type": "freeze"}
pipeline.run(data=my_source, schema_contract="freeze")
Hierarquia do contrato: source → resource → run

O contrato definido no @dlt.source vale como default para todos os resources; o do @dlt.resource sobrescreve para aquele resource; e o passado em pipeline.run() sobrescreve tudo naquela execução. Precisão na medida certa: fonte congelada, com uma tabela específica evoluindo.

Nuances que evitam sustos

  • Tabelas novas são sempre permitidas na primeira vez: na primeira carga de uma tabela, o modo de colunas vira evolve internamente (para permitir a inferência inicial) e volta ao original depois.
  • Contratos aplicam após normalização de nomes: createdAt já é created_at quando o contrato avalia.
  • discard_row é por tabela: se a violação é numa nested table (users__addresses), a linha da tabela filha cai, mas a linha pai em users é carregada.
  • Em freeze, o dlt lança DataValidationError com contexto completo: schema_name, table_name, column_name, o dado que causou a violação e o contrato expandido. Você captura com PipelineStepFailed e sabe exatamente o que a fonte mudou.

Pydantic + schema contracts

Você pode usar modelos Pydantic como schema via columns=MeuModelo. O Pydantic valida tipos antes do dlt aplicar o contrato — duas camadas de proteção. O dlt mapeia os modos do contrato para o extra do Pydantic:

Modo de colunasPydantic extra
evolveallow
freezeforbid
discard_valueignore
discard_rowforbid + tratamento da ValidationError
from pydantic import BaseModel

class Game(BaseModel):
    model_config = {"extra": "forbid"}   # ⇒ columns="freeze"
    id: int
    slug: str
    name: str

@dlt.resource(columns=Game)
def games():
    ...

Extensibilidade: Python puro é a vantagem

O dlt foi desenhado para ser estendido em Python — não há DSL proprietária, YAML complexo ou plugin system fechado. Quando você precisa de algo que o dlt não faz out-of-the-box, você escreve Python:

Custom destination

# Implemente a interface de destination para qualquer sistema
from dlt.destinations import Destination

# Weaviate, Qdrant e outros destinos "não-SQL" são implementados assim

Custom source

# Qualquer fonte que yielda dados é um source válido
@dlt.source
def minha_fonte_exotica(config=dlt.secrets.value):
    for batch in protocolo_maluco.fetch():
        yield dlt.resource(batch, name="dados")

Custom incremental strategy

# incremental() aceita funções lambda para lógica customizada
incremental(
    "updated_at",
    initial_value=0,
    transformer=lambda x: x.isoformat()  # transforma antes de comparar
)

Custom normalizer

O próprio normalizer é plugável: você pode trocar a forma como listas aninhadas são ligadas às tabelas pai, ou gerar estruturas estilo parquet. Isso é profundo — mas existe, documentado, para quem precisar.

Essa extensibilidade é o argumento central para equipes que cresceram além de scripts caseiros mas não querem as amarras de plataformas de conectores. O Python é a linguagem de extensão — e é a mesma linguagem do resto da codebase.

dlt + DuckDB: o "data lake on a laptop"

DuckDB é o destino mais comum em desenvolvimento. Com ele, você tem um ciclo de feedback ultra-rápido: extrai, carrega, inspeciona com SQL ou DataFrame — tudo local, sem servidor. E como vimos na Aula 1, esse padrão explodiu: dispositivos únicos usando DuckDB via dlt cresceram 15x em um ano.

pipeline = dlt.pipeline(destination="duckdb", dataset_name="rawg_data")
pipeline.run(data=rawg().add_limit(max_items=100))

# Inspeciona no próprio Python
df = pipeline.dataset().games.df()

# Ou conecta com DBeaver, MotherDuck, etc.

dlt + dbt: ingestão + transformação

dlt lida com EL (Extract e Load); dbt lida com T (Transform). O dlt gera schemas limpos e tipados que o dbt consome diretamente. O load_info do dlt pode disparar jobs dbt após a carga:

# Exemplo de integração dlt → dbt em Airflow
load_info = pipeline.run(data=source)
if load_info.loads_ids:
    dbt_run()  # transforma os dados recém-carregados

dlt + orquestradores (Airflow, Dagster, Prefect)

O dlt roda em qualquer lugar que rode Python. Não precisa de runtime especial:

  • Airflow: cada pipeline.run() vira uma task no DAG. O dlt gerencia estado entre execuções — o Airflow só precisa disparar na schedule certa.
  • Dagster: resources do dlt podem ser expostos como Dagster ops/assets.
  • Prefect: similar. O pipeline.run() é uma Python function que o Prefect gerencia.
  • Serverless: Lambda, Cloud Functions, Cloud Run — pip install dlt e pronto. O estado no destino torna cada invocação stateless.

dlt + Ibis: transformações Python-para-SQL

O Ibis permite escrever transformações em Python que são compiladas para SQL e executadas diretamente no destino (DuckDB, Snowflake, BigQuery...). O dlt integra nativamente:

import ibis

dataset = pipeline.dataset()
games = dataset.games.to_ibis()   # lazy Ibis expression

# Agregação em Python, execução em SQL no destino
# (esrb_rating__name é a coluna achatada de esrb_rating.name)
jogos_por_classificacao = (
    games
    .group_by("esrb_rating__name")
    .aggregate(total=ibis._.id.count())
)

# Só aqui o SQL roda
print(jogos_por_classificacao.to_pyarrow())
Zero-copy

Os dados não passam pela memória do Python: Ibis compila para SQL, o destino executa. É o mesmo padrão de composição que Arrow e Ibis foram desenhados para suportar — e que o dlt respeita de ponta a ponta.

dlt + Marimo: notebooks interativos

Marimo é um notebook reativo onde células reexecutam automaticamente quando dependências mudam. O dlt tem integração direta para visualização e exploração dos datasets carregados.

dltHub Platform + agentic workflows

Além da biblioteca open-source, a dltHub (GA desde mai/2026, Aula 1) transforma pipelines dlt em produção com agentes:

  • AI Workbench: coding agents (Claude, Codex, Cursor) geram, depuram e fazem deploy de pipelines.
  • dltHub Context: catálogo com 10.100+ fontes REST API pré-pesquisadas para os agentes consumirem.
  • Managed runtime: deploy com um comando. Scheduling, alerting, observabilidade, transform-aware triggers.
  • Ibis-powered transformations: agentes propõem transformações em Python → compilam para SQL → executam no DuckDB/Snowflake.

Em 2026, 91% dos pipelines dlt são gerados por coding agents — o dlt virou, nas palavras da própria empresa, "o runtime de ingestão de dados".
