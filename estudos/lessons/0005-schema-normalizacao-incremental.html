Aula 5: Schema, normalização e incremental loading

Objetivo: Entender como o dlt infere schemas, achata dados aninhados em tabelas relacionais, lida com tipos divergentes (variant columns) e implementa carga incremental com cursor e merge strategies.
Requer: Aula 4.
Fonte primária: Schema e Incremental loading (docs oficiais).

Schema inference: como o dlt "entende" seus dados

Quando um resource yielda dados, o dlt infere o schema automaticamente na fase de normalize. Ele observa os registros, detecta tipos, e gera a estrutura da tabela:

# Exemplo: o dlt infere "id" como bigint, "name" como text,
# "rating" como double precision, "metacritic" como bigint e
# "updated" como timestamp (detector de ISO 8601)
@dlt.resource
def games():
    yield {"id": 3498, "name": "Grand Theft Auto V",
           "rating": 4.47, "metacritic": 96,
           "updated": "2026-06-03T12:00:00"}

A inferência usa detectors configuráveis — o detector de ISO 8601 (string de data vira timestamp) vem habilitado por padrão. Você pode adicionar/remover detectors, definir preferred types por regex (ex.: toda coluna *_at vira timestamp) e regras de hints globais:

# preferred types: colunas que casam o padrão ganham o tipo
settings:
  preferred_types:
    re:timestamp: timestamp
    created_at: timestamp
    updated_at: timestamp

Se registros posteriores trazem colunas novas, o dlt evolui o schema automaticamente (modo evolve). Isso é controlável com schema contracts — Aula 6.

Naming conventions

O dlt traduz identificadores para o namespace que o destino aceita. O padrão: snake_case minúsculo, só alfanuméricos e underscore, e aninhamento expresso com __ duplo:

# "createdAt" → created_at; "CamelCase" → camel_case
# chave "esrb_rating" { "name" } → coluna esrb_rating__name

A mesma convenção vale para todos os destinos — você vê os mesmos nomes de tabelas e colunas em DuckDB, Snowflake ou Postgres. (Se quiser manter camelCase literal, existe a convenção direct — mas os docs recomendam: "use nomes simples, curtos, minúsculos".)

Normalização de dados aninhados

Este é um dos recursos mais poderosos do dlt. Dados JSON com nested lists e dicts são automaticamente "achatados" em tabelas relacionais:

# Item do endpoint /games — campos e tipos conforme a spec Swagger
# oficial da RAWG (api.rawg.io/docs); valores ilustrativos
{
    "id": 3498,
    "slug": "grand-theft-auto-v",
    "name": "Grand Theft Auto V",
    "rating": 4.47,
    "updated": "2026-06-03T12:00:00",
    "platforms": [
        {"platform": {"id": 4, "name": "PC", "slug": "pc"},
         "released_at": "2015-04-14"},
        {"platform": {"id": 18, "name": "PlayStation 4", "slug": "playstation4"},
         "released_at": "2014-11-18"}
    ],
    "esrb_rating": {"id": 4, "name": "Mature", "slug": "mature"},
    "added_by_status": {"owned": 13165, "toplay": 720}
}

# Schema gerado pelo dlt:
# Tabela raiz: games
# Colunas: id, slug, name, rating, updated, esrb_rating__id,
#          esrb_rating__name, esrb_rating__slug, added_by_status__owned,
#          added_by_status__toplay (dicts → colunas com __)
# Tabela aninhada: games__platforms (lista → tabela filha)
# Colunas: platform__id, platform__name, platform__slug, released_at,
#          _dlt_parent_id, _dlt_list_idx

Anatomia das colunas de sistema

ColunaHintFunção
_dlt_idrow_keyIdentidade única da linha. Em root tables: string aleatória (ou hash determinístico do primary_key no merge). Em nested tables: hash de parent + posição na lista.
_dlt_load_id—Qual load package trouxe a linha (linhagem até a execução)
_dlt_parent_idparent_keyFK para o _dlt_id da linha pai
_dlt_root_idroot_keyFK direto para a root table, pulando pais intermediários (necessário para merge)
_dlt_list_idx—Posição do elemento na lista aninhada original

O conjunto parent + row_key + parent_key forma a nested reference — a chave estrangeira relacional que liga as tabelas. É o que permite que replace e merge funcionem corretamente em dados aninhados.

max_table_nesting

Você controla a profundidade da normalização:

# 0: nada é expandido, tudo vira JSON
@dlt.resource(max_table_nesting=0)

# 1: só expande um nível de listas/dicts
@dlt.resource(max_table_nesting=1)

# 2-3: recomendado para produzir schemas mais legíveis
@dlt.source(max_table_nesting=2)

Variant columns: quando os tipos divergem

O normalizer padrão tenta coerção entre tipos compatíveis ("123" → int, int → text). Quando a coerção falha, o dlt cria uma variant column em vez de quebrar:

# Rodada 1: metacritic é bigint
[ {"metacritic": 96} ]

# Rodada 2: a fonte mandou uma string não-numérica
[ {"metacritic": 96}, {"metacritic": "tbd"} ]

# Schema resultante: coluna metacritic (bigint) + coluna metacritic__v_text (text)
# Valores que não couberam em bigint vão para metacritic__v_text
Controle fino de tipos

Existe um normalizer alternativo (relational_no_coercion) que nunca converte entre tipos — todo mismatch vira variant column. E se uma coluna específica deve ser tratada como JSON bruto (sem flattening), force com columns={"col": {"data_type": "json"}}.

Incremental loading: só o que mudou

Carregamento incremental significa trazer apenas dados novos ou modificados — baixa latência, baixo custo. O dlt faz isso com dlt.sources.incremental:

import dlt
from dlt.sources import incremental

@dlt.resource(primary_key="id", write_disposition="merge")
def games(
    updated_at=dlt.sources.incremental(cursor_path="updated", initial_value="1970-01-01T00:00:00")
):
    # `updated_at.last_value` contém o maior timestamp já carregado
    # e a RAWG aceita filtro por intervalo: updated=DATA,DATA
    dados = client.paginate(path="games", params={
        "updated": f"{updated_at.last_value},{agora}",
    })
    yield from dados

O dlt persiste o cursor (last_value) no pipeline state entre execuções. Na próxima rodada, updated_at.last_value automaticamente começa de onde parou. É o mecanismo que torna o pipeline resumível — inclusive de outra máquina, já que o state vive no destino.

Como funciona internamente

  1. Primeira execução: carrega do initial_value até o presente. O dlt registra o maior valor de updated_at encontrado.
  2. Segunda execução: o resource começa do último last_value registrado. Só dados novos ou modificados são carregados.
  3. Com write_disposition="merge": faz upsert com base na primary_key. Registros existentes são atualizados, novos são inseridos.

Escolhendo a write disposition: o fluxograma

A primeira pergunta é: meus dados são stateful ou stateless?

Dados imutáveis (evento, log, page view)?
  → stateless → append

Dados mutáveis (perfil de usuário, catálogo)?
  → stateful
      Precisa manter histórico de mudanças?
        → SIM → SCD2 (dimensões que mudam lentamente, tipo 2)
        → NÃO → dá para pedir só "o que mudou desde ontem"?
            → SIM → merge (upsert incremental)
            → NÃO → replace (full refresh)

Merge strategies

EstratégiaComportamentoQuando usar
upsert (padrão)Insere novos, atualiza existentes por primary_keyCRM, catálogos, entidades com ID estável
delete-insertDeleta registros do batch e insere tudo de novoFontes que mandam snapshot completo da entidade
SCD2Mantém histórico completo com _dlt_valid_from / _dlt_valid_toDimensões que mudam lentamente (cliente trocou de cidade)

Pipeline state: a memória do pipeline

O estado é um dicionário Python que vive ao lado dos seus dados: você grava valores numa execução e os lê na próxima. Internamente, o dlt o usa para o que você já viu nesta aula:

  • Cursor values — o last_value de cada incremental.
  • Schema versions — o histórico de schemas por tabela.
  • Custom state — qualquer estado que você mesmo escrever.

No nosso exemplo, o RAWg já usa o estado sem você escrever uma linha: o cursor do dlt.sources.incremental é persistido ali automaticamente. Depois de rodar o pipeline, dá para inspecioná-lo em pipeline.state — é exatamente o que o smoke_test.py verifica:

# onde o cursor incremental do RAWg vive no pipeline state
state = pipeline.state
games_state = state["sources"]["rawg"]["resources"]["games"]
cursor = games_state["incremental"]["updated"]["last_value"]
# → "2026-06-03T12:00:00" — o maior `updated` já carregado

Isso cobre ~90% do uso de estado. Para o restante — estado customizado — o dlt expõe dois escopos de acesso:

EscopoAPIVisibilidade
Sourcedlt.current.source_state()Compartilhado entre os resources do source; read-only na função do source
Resourcedlt.current.resource_state()Privado de um resource específico
dlt.current.state() é source_state

O nome dlt.current.state() ainda existe, mas é um alias de source_state() (source-scoped) — não um "estado global do pipeline" separado. Verificado no código 1.30.0: dlt/pipeline/current.py tem state = source_state. O estado do pipeline inteiro (todos os sources/resources) fica em pipeline.state.

O padrão mais comum: guardar uma lista do que já foi processado no escopo do resource, para não reprocessar (ex.: arquivos já baixados):

@dlt.resource(write_disposition="append")
def players_games(chess_url, player):
    # resource-scoped: privado deste resource
    checked = dlt.current.resource_state().setdefault("archives", [])
    for url in _archives(chess_url, player):
        if url in checked:
            continue
        checked.append(url)
        yield from _get_games(url)

O estado precisa ser JSON-serializável (o dlt trata DateTime, Decimal, bytes e UUID além dos tipos padrão).

Onde o estado mora — e como ele viaja

O estado é salvo no working dir local e sincronizado com o destino, na tabela _dlt_pipeline_state. A identidade do estado remoto é: nome do pipeline + localização do destino + dataset. É isso que torna o pipeline resumível de outra máquina.

  • Em orquestradores com filesystem limpo (Airflow), o dlt restaura o estado do destino automaticamente.
  • dlt pipeline sync pede o estado de volta manualmente.
  • Se você mantém o working dir entre runs, desligue o sync com restore_from_destination=false no config.toml.

Quando NÃO usar o estado

Não use o estado se ele pode crescer para milhões de registros (ex.: timestamp de modificação de cada usuário). Nesse caso, use os próprios dados como estado — o dlt expõe o pipeline atual para consultar o destino, com first_run para evitar consultar uma tabela que ainda não existe:

@dlt.resource(name="user_comments")
def comments(user_id):
    pipeline = dlt.current.pipeline()
    max_id = 0
    if not pipeline.first_run:   # na 1ª execução a tabela ainda não existe
        table = pipeline.dataset().table("user_comments").to_ibis()
        # seleciona max(_id) para este user_id e usa como filtro
        ...
    yield from dados_filtrados_por_max_id

Resetando o estado

  • Total: dropar o dataset do destino, dev_mode=True, ou dlt pipeline <nome> drop --drop-all.
  • Parcial: dlt pipeline <nome> drop <resource> (estado + tabela de um resource) ou --state-paths (reseta um caminho específico do estado sem tocar tabelas/dados).

Lag / attribution window

APIs de analytics costumam "corrigir" dados retroativamente (eventos que chegam atrasados). Para isso, o incremental aceita um lag: o cursor não avança até o "agora", mas até agora - lag — e na próxima rodada a janela é revisada. Com merge no lugar, dados corrigidos são atualizados em vez de duplicados.

Exemplo do curso: o que a RAWG vira no destino

O endpoint /games da RAWG é uma aula de JSON aninhado — e o /games/{id} (usado pelo transformer game_details) ainda mais. Veja o que o dlt gera a partir de cada um (código em exemplos/rawg/; o smoke_test.py valida exatamente estas tabelas):

# Item do /games — campos e tipos conforme a spec Swagger oficial da RAWG
{
  "id": 3498, "name": "Grand Theft Auto V", "updated": "2026-06-03T12:00:00",
  "platforms": [{"platform": {"id": 4, "name": "PC", "slug": "pc"}, "released_at": "2015-04-14"}, ...],
  "esrb_rating": {"id": 4, "name": "Mature", "slug": "mature"},
  "added_by_status": {"owned": 13165, "toplay": 720}
}

# Tabelas geradas (verificadas contra um run real, set/2026):
# games            → id, name, updated, esrb_rating__name,
#                    added_by_status__owned, ... (dicts → colunas __)
# games__platforms → lista aninhada (com requirements_en__* —
#                    a própria RAWG já nomeia requirements_en/_ru)
# games__genres, games__tags, games__stores, games__ratings,
# games__short_screenshots, games__parent_platforms → idem

# E o transformer: /games/{id} (GameSingle) gera mais nested tables
# game_details                        → description, website, ...
# game_details__platforms, __metacritic_platforms, __alternative_names,
# __developers, __publishers, __genres, __tags, __stores, __ratings,
# __parent_platforms → 24 tabelas no total (genres__games inclusive)

O incremental do exemplo usa um recurso nativo do dlt: a RAWG aceita tanto o filtro updated=DATA,DATA (intervalo) quanto ordering=-updated (mais novos primeiro). Declarando row_order="desc" no cursor, o dlt para de pedir páginas sozinho quando encontra um registro mais antigo que o cursor, filtra o já carregado e deduplica pelo primary_key — o resource só cuida da paginação pura:

# o cursor declara a ordem dos dados; o resource só pagina
@dlt.resource(write_disposition="merge", primary_key="id")
def games(
    client,
    updated_at=dlt.sources.incremental(
        cursor_path="updated", initial_value="1970-01-01T00:00:00", row_order="desc"
    ),
):
    ...
