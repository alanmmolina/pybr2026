Aula 2: Arquitetura central — as três fases e os quatro conceitos

Objetivo: Compreender a anatomia do dlt — resource, source, pipeline e destination — e o ciclo extract → normalize → load que acontece em cada execução.
Requer: Aula 1.
Fonte primária: How dlt works (docs oficiais).

Visão panorâmica

O dlt organiza a ingestão de dados em quatro conceitos fundamentais. Entender como eles se relacionam é meio caminho andado:

O Pipeline é o orquestrador. Ele recebe um Source (ou um Resource avulso), extrai os dados, normaliza (inferência de schema, flattening de estruturas aninhadas) e carrega no Destination. Tudo isso com estado persistido entre execuções para viabilizar carregamento incremental.

As três fases: o que acontece dentro de pipeline.run()

Chamar pipeline.run() dispara três fases discretas. Cada uma pode ser executada isoladamente — e entender essa separação explica muita coisa sobre como o dlt é tolerante a falhas.

# O menor pipeline possível — o exemplo canônico dos docs
import dlt

pipeline = dlt.pipeline(pipeline_name="my_pipeline", destination="duckdb")
pipeline.run(
    [
        {"id": 1},
        {"id": 2},
        {"id": 3, "nested": [{"id": 1}, {"id": 2}]},
    ],
    table_name="items",
)

O que acontece por trás, fase a fase:

1. Extract — extrai tudo para o disco

O dlt extrai os dados da fonte integralmente para o disco rígido, em um load package: um diretório com ID único que contém os dados crus exatamente como vieram da fonte. No exemplo acima, um source implícito com um resource de 3 itens é criado e extraído.

Você pode rodar só a extração:

pipeline.extract(data)   # só extrai; nada vai para o destino

Nesta fase você controla: limites e amostragem, cursores incrementais, paralelização, e pode aplicar filtros/maps para pseudonimizar ou remover dados pessoais.

2. Normalize — inspeciona e computa o schema

O dlt inspeciona e normaliza os dados, computando um schema compatível com o destino. Para o exemplo: detecta uma coluna id do tipo int na tabela items, detecta a lista aninhada em nested e a transforma em uma tabela filha items__nested. O schema evolui automaticamente quando a fonte muda (colunas/tabelas novas).

O resultado é um load package atualizado com os dados em formato que o destino entende + o schema completo. Você controla: nível máximo de aninhamento, schema contracts, e performance.

pipeline.normalize()   # só normaliza; exige extract concluído

3. Load — migra schema e carrega em chunks

O dlt roda as migrações de schema necessárias no destino e então carrega os dados em pedaços menores chamados load jobs (permite paralelizar cargas grandes). Se a conexão com o destino cair, é seguro reexecutar o pipeline: o dlt continua de onde parou, load job por load job.

pipeline.load()   # só carrega; exige normalize concluído
Por que a separação em fases importa

Extract é a única fase que conversa com a fonte; Load é a única que conversa com o destino. Entre elas, tudo é persistido em disco. Isso significa: fonte lenta não trava o destino, falha de rede no meio do load não perde o que já foi extraído, e cada fase pode ser reprocessada independentemente.

Resource

Um resource é a unidade fundamental de extração. No código, é uma função Python decorada com @dlt.resource que yielda dados. Pode ser um generator síncrono, async generator, ou retornar listas, DataFrames, Arrow tables.

import dlt

@dlt.resource(write_disposition="merge", primary_key="id")
def games():
    # campos conforme a spec Swagger da RAWG (api.rawg.io/docs)
    yield {"id": 3498, "slug": "grand-theft-auto-v",
           "name": "Grand Theft Auto V",
           "released": "2013-09-17", "rating": 4.47,
           "metacritic": 96}

Na analogia: se o Source é uma API REST, cada Resource é um endpoint. Se o Source é um banco SQL, cada Resource é uma tabela. Se é uma planilha, cada Resource é uma aba. O Resource completo (hints, transformers, filtros) fica na Aula 3.

Source

Um source é um agrupamento lógico de resources. No código, é uma função decorada com @dlt.source que retorna um ou mais resources. Ele tipicamente encapsula a lógica de autenticação e configuração compartilhada:

import dlt

@dlt.source
def rawg(api_key=dlt.secrets.value):
    # autenticação e paginação declaradas uma vez, no client
    client = RESTClient(base_url=API_URL,
        auth=APIKeyAuth(name="key", location="query", api_key=api_key),
        paginator=JSONLinkPaginator(next_url_path="next"))
    return genres(client=client), games(client=client)

Source em profundidade: eager, seleção e customização

Um detalhe de arquitetura que muita gente erra: a função do source é eager — executa no instante em que você a chama — enquanto os resources são lazy, como generators, adiando a extração para o pipeline.run(). Por isso os docs recomendam: não extraia dados dentro da função do source; deixe isso para os resources (você ganha error handling, métricas de execução e paralelismo).

O source expõe os resources num dicionário .resources, e você pode selecionar o que carregar sem tocar no código do source:

from rawg import rawg
source = rawg()

source.resources.keys()          # todos os resources disponíveis
source.resources.selected.keys() # só os selecionados para carregar
print(source.games.selected)         # resource acessível como atributo

# carrega só games e genres; game_details fica de fora
pipeline.run(data=source.with_resources("games", "genres"))

source.games.selected = False   # desseleciona individualmente

Outros mecanismos de customização pós-criação:

  • clone(name=..., section=...) — renomeia o source (muda o namespace de config para [sources.<novo>]) e permite várias instâncias lado a lado.
  • source.resources.add(source.deals | deal_scores) — adiciona um transformer novo a um source existente (o dlt clona o resource; sua instância original não é afetada).
  • source.schema — acesso ao schema para ajustá-lo antes da carga; source.root_key propaga o _dlt_id da raiz para as nested tables.
Gotcha: max_table_nesting no source

O max_table_nesting definido no source não se propaga para um resource acessado direto via source.resources["x"]. Para valer, use source.with_resources("x") ou sete o parâmetro no próprio resource.

Fonte: Source (docs oficiais).

Pipeline

O pipeline conecta source a destination. Gerencia o ciclo de vida completo (extract, normalize, load), mantém estado entre execuções e rastreia schemas:

import dlt

pipeline = dlt.pipeline(
    pipeline_name="rawg",
    destination="duckdb",
    dataset_name="rawg_data",
)
load_info = pipeline.run(data=rawg())
print(load_info)  # métricas da execução

O pipeline persiste tudo no diretório ~/.dlt/pipelines/<nome>/: schemas, estado, traces, load packages. Você pode reconectar a um pipeline anterior com dlt.attach() — profundidade completa na Aula 4.

Destination

O destination é onde os dados caem. O dlt suporta 20+ destinos, trocáveis mudando uma string:

TipoExemplos
Data warehousesSnowflake, BigQuery, Redshift, Databricks
Bancos SQLPostgreSQL, MySQL, DuckDB, MotherDuck, ClickHouse
Data lakesS3, GCS, Azure Blob Storage
Formatos abertosIceberg, Delta Lake
Vector DBsWeaviate, Qdrant

O mesmo código funciona em qualquer destino. O dlt cuida de: DDL no dialeto do destino, mapeamento de tipos, staging (S3/GCS para warehouses que exigem stage antes do COPY) e schema drift. Detalhes na Aula 4.

As tabelas internas que o dlt cria no destino

Além das suas tabelas de dados, o dlt cria tabelas especiais no dataset — não se assuste ao vê-las; elas são a maquinaria interna:

TabelaFunção
_dlt_loadsRegistro de cada load package (load ID, status, timestamps)
_dlt_pipeline_stateEstado do pipeline (cursores incrementais, etc.) — permite restaurar execuções em outra máquina
_dlt_versionHash/versão do schema atual — o dlt compara para saber se precisa migrar

E nas tabelas de dados, colunas de sistema: _dlt_id (identidade única da linha), _dlt_load_id (qual load trouxe a linha), e nas tabelas aninhadas _dlt_parent_id + _dlt_list_idx. Anatomia completa na Aula 5.

O fluxo completo

import dlt

# Versão simplificada: sem transformer (Aula 3) nem incremental (Aula 5)
# 1. Define o source (autenticação compartilhada + agrupa resources)
@dlt.source
def rawg(api_key=dlt.secrets.value):
    client = RESTClient(base_url=API_URL,
        auth=APIKeyAuth(name="key", location="query", api_key=api_key),
        paginator=JSONLinkPaginator(next_url_path="next"))
    return genres(client=client), games(client=client)

# 2. Cada resource extrai dados (campos da spec Swagger da RAWG)
@dlt.resource(write_disposition="merge", primary_key="id")
def games(client):
    yield {"id": 3498, "slug": "grand-theft-auto-v",
           "name": "Grand Theft Auto V",
           "released": "2013-09-17", "rating": 4.47}
    # produção: for page in client.paginate(path="games", ...): yield from page

@dlt.resource(write_disposition="replace")
def genres(client):
    yield {"id": 4, "name": "Action", "slug": "action",
           "games_count": 190000}

# 3. Pipeline conecta ao destino e carrega
pipeline = dlt.pipeline(
    pipeline_name="rawg",
    destination="duckdb",
    dataset_name="rawg_data",
)
pipeline.run(data=rawg())

# 4. Lê os dados de volta como DataFrame
print(pipeline.dataset().games.df())

Exemplo do curso: RAWG → data lake

Todas as aulas usam um exemplo real e funcional: ingerir a RAWG Video Games API (500k+ jogos, gratuita com API key) para um data lake. O código completo está em exemplos/rawg/ e roda de verdade:

# exemplos/rawg/rawg.py — RAWG → DuckDB em 6 linhas
import dlt
from rawg import rawg

pipeline = dlt.pipeline(
    pipeline_name="rawg",
    destination="duckdb",      # ← mude para "filesystem" e vira data lake
    dataset_name="rawg_data",
)
# add_limit: cada jogo custa 1 request extra de detalhe; o free tier
# tem 20k requests/mês — a amostra respeita o orçamento da API
pipeline.run(data=rawg().add_limit(max_items=100))

O source usa um resource games com incremental, um resource genres e um transformer game_details que enriquece cada jogo com /games/{id} — os três conceitos desta aula em ação. Detalhes nas aulas 3-5.
